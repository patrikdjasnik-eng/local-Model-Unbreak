Model Clone is a planned workflow for turning a larger teacher model into a smaller model or adapter specialized for the user's actual workload.

It is **not** byte-for-byte copying of a model and must not be marketed as preserving the full intelligence or capability of the teacher.

## Purpose

A large model may run slowly on constrained hardware while a smaller specialized model can be fast enough for daily work.

Model Clone aims to answer:

> Can a smaller model reproduce enough of the teacher's behavior for the tasks this user actually performs?

Example:

```text
Teacher
Qwen-class 32B
      ↓
selected / synthetic examples
      ↓
curated training set
      ↓
student model
3B / 7B
      ↓
LoRA / QLoRA / distillation
      ↓
evaluation
      ↓
optional GGUF export
```

## Clone modes

### Quick Clone

Target: low-cost personalization.

Typical approach:

- small curated dataset,
- LoRA adapter,
- short training run,
- focused evaluation.

### Personal Clone

Target: a smaller model optimized around the user's recurring tasks.

Typical approach:

- synthetic examples generated by a teacher,
- explicitly selected user examples,
- LoRA/QLoRA or equivalent fine-tuning,
- teacher/student evaluation,
- exportable local artifact when supported.

### Deep Clone

Target: research-grade specialization.

Typical approach:

- larger dataset,
- multiple training/evaluation iterations,
- broader benchmark suite,
- stronger hardware requirements,
- optional remote trusted compute.

Deep Clone remains research/premium territory until the workflow is reliable and reproducible.

## Data consent

No personal dataset source is enabled silently.

The UI must present individual toggles:

```text
Data sources

[ ] Synthetic data only
[ ] Selected conversations
[ ] Selected coding sessions
[ ] Selected folders
[ ] Custom dataset
[ ] Imported benchmark set

[ Review selected data ] [ Continue ]
```

The default is **Synthetic data only**.

Selecting a folder grants access only to the chosen scope for the current clone job unless the user explicitly saves that permission.

## Data minimization

Before training, the user should be able to preview:

- included examples,
- excluded examples,
- detected secrets,
- file types,
- total records,
- estimated token count.

A future scrubber may remove or flag API keys, private keys, passwords, access tokens, connection strings, and other obvious secrets before a dataset can be approved.

## Teacher-generated data

Synthetic generation should be auditable:

```text
task template
    ↓
teacher prompt
    ↓
teacher response
    ↓
quality filter
    ↓
dataset candidate
    ↓
user-visible sample / approval policy
```

Reasoning traces should not be assumed available or required. The workflow trains on outputs and structured supervision that the teacher/runtime is actually permitted to expose.

## Evaluation

A clone is not accepted merely because training completed.

Evaluation should compare:

- task success,
- correctness,
- latency,
- tokens/s,
- memory use,
- regressions outside the target domain,
- teacher/student agreement on a held-out set.

Example:

```text
MODEL CLONE RESULT

Teacher: 32B
Student: 7B + LoRA

Coding task pass rate
Teacher    91%
Student    86%

Generation speed
Teacher     7 tok/s
Student    26 tok/s

VRAM target
Teacher    hybrid
Student    local GPU

Recommendation
SUITABLE FOR DAILY CODING
Teacher still preferred for hard reasoning.
```

Numbers shown here are illustrative only.

## Artifact states

A clone can be:

- `TRAINING`,
- `EVALUATING`,
- `CANDIDATE`,
- `APPROVED`,
- `REJECTED`,
- `ARCHIVED`.

The user should be able to keep multiple clone versions and compare them.

## Security

Training runs inherit Security Lab policy.

When user data is included:

- remote training requires explicit approval,
- remote nodes must be trusted/attested,
- dataset transfer must be visible,
- temporary training data must be cleaned up according to policy,
- prompts/files must not enter generic telemetry.

## Free / Premium boundary

Planned product boundary:

### Free

- one active Quick Clone,
- synthetic-data-only by default,
- local LoRA workflow where supported,
- basic evaluation.

### Premium

- Personal/Deep Clone workflows,
- multiple clone profiles,
- selected local data sources,
- richer evaluation,
- trusted remote training,
- automatic retraining experiments,
- stronger planner integration.

The upstream model license always takes precedence over product tier.

## Implementation status

This is a design specification. No cloning capability should be marked production-ready before reproducible training, evaluation, privacy, and cleanup tests exist.
